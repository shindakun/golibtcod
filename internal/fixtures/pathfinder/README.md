# Pathfinder fixtures

Unlike every other fixture directory here, these are **not** generated by
stock libtcod. They come from a C build of `pathfinder.c` with four upstream
defects corrected, because the module as shipped cannot compute a path at
all.

`pathfinder_corrected.c.txt` is that patched source, committed so the
comparison is reproducible and the patches are auditable.

## The upstream defects

All four verified against libtcod HEAD `c54823e` (2026-07-07), read live
through the GitHub contents API rather than a local clone.

**1. `TCOD_pf_in_bounds` rejects every positive coordinate** (line 144)

```c
if (0 < index[i] || (size_t)index[i] >= path->shape[i]) return false;
```

The first test should be `0 > index[i]`. As written only `(0,0)` is ever in
bounds, so the search cannot leave the origin cell. Extracting the condition
verbatim and running it gives `in_bounds(0,0)=1` and `in_bounds(1,0)=0`.

**2. The relaxation test is inverted** (line 156)

```c
int total_dist = array_get(&path->distance, origin) + cost;
if (array_get(&path->distance, dest) >= total_dist) return;
```

Distances are seeded to `INT_MAX`, so an unvisited neighbour always
satisfies `>=` and the function returns before relaxing anything.

**3. The cost grid is never read** (lines 258-263)

`TCOD_pf_set_graph2d_pointer` populates `path->graph.cost`, and nothing ever
reads it: the only `array_get` calls in the file target `distance`. Every
edge therefore costs the flat cardinal or diagonal constant, so walls and
terrain costs supplied by the caller have no effect.

**4. A stride is stored in a shape field** (line 281)

```c
path->traversal.shape[i] = strides[i];
```

`shape` holds dimension lengths; `strides` holds byte offsets. Only reachable
when a traversal pointer is set, which this harness does not do.

Consequence: `TCOD_pf_compute` is non-functional. Nothing inside libtcod
calls `TCOD_pf_*` or `TCOD_frontier_*`, so the breakage is invisible there;
the module exists as a backend for python-tcod.

No upstream issue or pull request covers any of this. Searched issues in all
states for `pathfinder`, `in_bounds`, `TCOD_pf` and `pf_in_bounds`, and pull
requests for `pathfinder in_bounds`.

## What the Go port implements

`path/pathfinder.go` implements the **intended** behaviour: bounds checked
correctly, relaxation toward lower distances, and the caller's cost grid
honoured with non-positive cells impassable. Porting the shipped behaviour
would produce a pathfinder that returns the origin and nothing else.

This is the one place in the project where the port deliberately does not
reproduce upstream, and it is recorded in the Deferred Register under
"Deviations from faithful porting".

## Regenerating

```
gcc -w -I<libtcod/src/libtcod> -I<libtcod/src> -o pf \
    gen_pathfinder.c pathfinder_corrected.c \
    pathfinder_frontier.c heapq.c error.c logging.c
./pf < corpus.txt > fixtures_pathfinder.txt
```

`corpus.txt` is 80 randomized cases: grids up to 12x12, cardinal and
diagonal weights from 0 to 14 (0 disabling that movement class), cost cells
including zeros and negatives as walls, and one to three seed roots. The
port reproduces all 80 distance fields exactly, and matched all 250 cases of
the wider generated set before it was trimmed for committing.
